# Taw Ijyk (توا يجيك)

Taw Ijyk is a queue and order-status app for businesses. Staff manage orders from a dashboard; customers scan a QR code and check an order without creating an account.

## What the app does

- Business accounts can sign up with email and password or Google.
- Password sign-up requires a six-digit email code. Codes expire after 15 minutes; users can request another code after the resend cooldown. Google verifies the email through Google.
- Staff create queue entries using an invoice number and estimated preparation time, extend waiting times, and mark orders ready.
- Customers scan a business QR code, enter an invoice number, and follow the order status. A customer can optionally enable an audible alert while tracking.
- Each business has its own order history, settings, QR code, and public customer tracking page.
- Business owners can edit their business name, phone number, password, and logo.
- The admin dashboard manages subscriptions and account status, and provides payment and account history.
- The interface supports dark and light themes.

## Technology and project layout

- **Client:** React 19, Vite, and plain CSS in `client/`.
- **API:** Node.js, Express, and CommonJS in `server/src/index.js`.
- **Database:** MongoDB with Mongoose models.
- **Authentication:** bcrypt password hashes, JWT sessions, and Google Identity Services.
- **Email:** Nodemailer over SMTP for password-signup verification.
- **Business logos:** Cloudinary signed uploads.
- **QR codes and posters:** generated by the client with the `qrcode` package.

```text
client/
  index.html                App entry page and browser title
  vite.config.js            Vite settings and development API proxy
  public/                   Logo, favicon, sounds, and QR poster assets
  src/main.jsx              App routes, screens, API calls, and UI logic
  src/styles.css            App styling and responsive layouts
server/src/
  index.js                  Express routes, integrations, and startup
  middleware/               Business auth, admin auth, subscription, and rate limit
  models/                   Business, order, and business event schemas
README.md                   Setup and project guide
```

## Requirements

- Node.js and npm
- MongoDB locally or a MongoDB Atlas database
- SMTP account for email/password sign-up
- Optional: Google Cloud OAuth client for Google sign-in
- Optional: Cloudinary account for business logo uploads

## Run locally

1. Install dependencies:

   ```sh
   npm install
   ```

2. Create a file named `.env` in the repository root. Start with the template below and replace the example values with your own.
3. Start MongoDB and ensure `MONGO_URI` points to the database.
4. Start both the API and client:

   ```sh
   npm run dev
   ```

5. Open `http://localhost:5173`.

The client uses Vite on port `5173`. During development, `/api` requests are proxied to the Express API on port `8000`. The API uses `PORT` if set, otherwise it listens on `8000`.

### Environment variables

```env
# Required
MONGO_URI=mongodb://127.0.0.1:27017/taw-ijyk
JWT_SECRET=replace-with-a-long-random-secret
CLIENT_ORIGIN=http://localhost:5173

# Required for email/password account verification
SMTP_HOST=smtp.example.com
SMTP_PORT=465
SMTP_USER=your-smtp-username
SMTP_PASSWORD=your-smtp-password
SMTP_FROM="Taw Ijyk <no-reply@example.com>"

# Optional: enable Google sign-in
GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
VITE_GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com

# Optional: enable business logo uploads
CLOUDINARY_CLOUD_NAME=your-cloud-name
CLOUDINARY_API_KEY=your-api-key
CLOUDINARY_API_SECRET=your-api-secret

# Optional: enable admin dashboard login (use a unique password of at least 16 characters)
ADMIN_PASSWORD=replace-with-a-strong-unique-password

# Optional: API port (defaults to 8000)
PORT=8000
```

Keep `.env` private. It is ignored by Git. Never commit SMTP passwords, `JWT_SECRET`, `ADMIN_PASSWORD`, or the Cloudinary API secret. `VITE_GOOGLE_CLIENT_ID` is included in the browser build; it is a public OAuth client ID, not a client secret. Do not put private credentials in any `VITE_` variable.

SMTP values come from your email provider. For Gmail, use `smtp.gmail.com`, port `465`, your full Gmail address as `SMTP_USER`, and a Google App Password as `SMTP_PASSWORD` (not your normal Google password). The sender address in `SMTP_FROM` should be permitted by your provider.

### Google sign-in setup

1. Create a **Web application** OAuth client ID in Google Cloud Console.
2. Add your app origin under **Authorized JavaScript origins**. For local development, use `http://localhost:5173`.
3. Set the same client ID for `GOOGLE_CLIENT_ID` and `VITE_GOOGLE_CLIENT_ID`.
4. Restart the dev server after changing `.env`.

The server validates Google's ID token. Google sign-up asks for a business name after the user selects their Google account. Google login is for existing accounts. If a verified Google email matches an existing password account, Google sign-in is linked to that account.

### Cloudinary logo uploads

Create a Cloudinary account and copy its cloud name, API key, and API secret into the three `CLOUDINARY_*` variables. Restart the server. Businesses can upload PNG, JPG, or WebP logos up to 5 MB from **Settings**. The server validates the image and signs the upload; MongoDB stores the resulting URL and Cloudinary stores the image.

### Admin dashboard

Set `ADMIN_PASSWORD` to a strong, unique password of at least 16 characters, restart the server, and visit `http://localhost:5173/#admin`. Admin access is unavailable until this password is configured.

## Pages and navigation

The client uses URL hashes for staff and admin pages:

| URL | Page |
| --- | --- |
| `/#login` | Business sign-in |
| `/#signup` | Business registration |
| `/#orders` | Live queue: create orders, extend waiting time, and mark orders ready |
| `/#dashboard` | Order history |
| `/#qr` | Business QR code and printable poster |
| `/#settings` | Business profile, logo, and password |
| `/#admin` | Admin subscriptions, account management, and history |

Customer pages use query parameters rather than a hash. The business QR code opens `/?customer&business=<public-business-code>&shop=<business-name>`. Customers enter an invoice number there to find an order. A direct tracking URL can use `/?customer=<order-token>&business=<public-business-code>`. The customer page does not grant access to the staff dashboard.

## API overview

Business endpoints that need a signed-in business account use the `Authorization: Bearer TOKEN` header. Admin endpoints need an admin JWT. Public customer routes do not need a login.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `POST` | `/api/auth/signup` | Create an email/password account and send a verification code |
| `POST` | `/api/auth/verify-email` | Verify an email code |
| `POST` | `/api/auth/resend-verification` | Resend an email code |
| `POST` | `/api/auth/login` | Sign in with email and password |
| `POST` | `/api/auth/google` | Sign up or sign in with a Google credential |
| `GET` | `/api/auth/me` | Get the signed-in business profile |
| `PATCH` | `/api/auth/business` | Update business details |
| `POST` / `DELETE` | `/api/auth/business/logo` | Upload or remove a business logo |
| `POST` | `/api/auth/password` | Set or change the account password |
| `GET` | `/api/orders` | List this business's orders |
| `POST` | `/api/orders` | Create an order (requires active subscription) |
| `POST` | `/api/orders/:id/extend` | Extend a waiting order (requires active subscription) |
| `POST` | `/api/orders/:id/ready` | Mark a waiting order ready (requires active subscription) |
| `GET` | `/api/public/business?business=<code>` | Get public business name and logo |
| `GET` | `/api/public/orders?invoice=<number>&business=<code>` | Look up an order by invoice |
| `GET` | `/api/public/orders/:token?business=<code>` | Get public order status |
| `POST` | `/api/admin/login` | Admin sign-in |
| `GET` | `/api/admin/businesses` | List business accounts and activity |
| `PATCH` | `/api/admin/businesses/:id/subscription` | Activate or update a subscription |
| `PATCH` | `/api/admin/businesses/:id/account-status` | Ban or unban an account |
| `DELETE` | `/api/admin/businesses/:id` | Permanently delete a business and its orders |
| `GET` | `/api/admin/history` | Read account and payment history |

## Data and business rules

MongoDB stores three main collections:

- **Business:** profile, email and password/Google identity, verification status, public QR code, account status, and subscription.
- **Order:** invoice, preparation time, queue status, timestamps, business owner, and an unguessable public tracking token.
- **BusinessEvent:** subscription changes, bans/unbans, and optional payment amounts recorded by the admin.

Orders are always filtered by the authenticated business ID for staff APIs. Public order lookups also require the business public code, so an order token is scoped to its business.

New business accounts start with an inactive subscription. Reading settings, order history, and QR pages remains possible without an active subscription; creating or changing queue orders requires a subscription that is active and has not expired.

The admin can set subscriptions for 30 days, 3 months, or 1 year, or enter a custom duration. Payment amounts are optional and must be entered to be included in revenue totals. The payment history cannot infer payments made before event tracking was introduced.

The server checks for expired accounts at startup and once per hour:

- Inactive accounts are permanently deleted after 14 days.
- Accounts with an expired active subscription are deleted 30 days after expiration.
- Banned accounts are not automatically deleted, keeping their email blocked.
- Automatic and manual deletion remove the business and its orders.

## Security and operations

- Passwords are hashed with bcrypt; verification codes are stored as hashes and are time-limited.
- Email verification codes expire after 15 minutes. A code is limited to five attempts; resend requests are subject to a one-minute cooldown.
- Business and admin sessions are JWTs. Business sessions last seven days; admin sessions last eight hours.
- Banning an account blocks its existing business sessions and future password/Google sign-in.
- Admin sign-in is limited to five failed attempts per IP per 15-minute window. This rate limit is in-memory and resets when the server restarts.
- Keep MongoDB, SMTP, Google, and Cloudinary credentials private. Use HTTPS and set `CLIENT_ORIGIN` to the real client origin when deploying.
- The Vite proxy is for local development. In production, deploy the built `dist/` client and the API, configure the production client origin, and route `/api` requests to the API server.
- Do not deploy the example SMTP, OAuth, or Cloudinary values.

## Useful commands

```sh
npm run dev       # Run the API and Vite client together
npm run server    # Run only the API
npm run client    # Run only the Vite client
npm run build     # Build the production client into dist/
```

There is no test script configured in `package.json`. For a quick server syntax check, run `node --check server/src/index.js`; for the frontend production build, run `npm run build`.

## Troubleshooting

- **The app cannot connect to the API:** keep `npm run dev` running and open the Vite URL at `http://localhost:5173`, not the API port.
- **MongoDB connection fails:** check that MongoDB is running and `MONGO_URI` points to the correct database.
- **Email sign-up fails:** verify all five `SMTP_*` settings, use provider-approved SMTP credentials, and restart the server after changing `.env`.
- **Google sign-in is missing or rejected:** check both Google client ID variables, authorized JavaScript origin, and restart the dev server.
- **Logo upload is unavailable:** configure all Cloudinary settings and restart the API.
- **Admin sign-in is unavailable:** set `ADMIN_PASSWORD` to at least 16 characters and restart the API.
- **An account cannot create orders:** ask the admin to activate or renew its subscription.

## Browser storage

The client stores the current business session and theme in browser storage. Customer invoice lookup remembers the most recent invoice for each business in that browser. Existing `dorak_*` storage entries are migrated to the current Taw Ijyk keys when read, so earlier sessions and preferences continue to work after the brand rename.
